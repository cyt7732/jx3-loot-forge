# 剑网3掉落工坊开发计划

> 文档版本：0.2.0（2026-08-25）
> 项目许可证：AGPL-3.0  
> 首发客户端：剑网3旗舰端 `client=std`  
> 正式分发：JX3BOX 帖子附件中的离线包；在线站点只承担预览

本文是当前已确认需求的实现基线。涉及危险操作（自动出售）的默认值、状态不变量、导入策略和导出格式均以本文为准。最后列出的“可后续调整策略”不阻塞第一版开发，但实现时要为其保留扩展点。

## 1. 产品目标与边界

剑网3掉落工坊是一个在网页中整理剑网3掉落物品，并生成游戏可直接导入配置文件的工具。用户可以一次选择多个历史副本、难度、Boss 和掉落物品，按物品类别批量设置“跳过拾取”“自动出售”“保护不出售”，也可以逐项调整，最后独立下载两个配置文件或一次下载两个文件。

第一版只采集和处理旗舰端（`client=std`）。怀旧端（`client=origin`）写入后续路线图，不在第一版数据或 UI 中假装支持。项目面向国内用户，但在线版本仅作为预览；完整源代码和可双击使用的离线包通过 JX3BOX 帖子附件提供。项目永不兼容 IE，只测试现代 Chrome、Edge、Firefox。

### 1.1 已确认的产品决策

- 正式使用场景是本地双击 `index.html`，不要求 Node、Web 服务器或联网。
- 在线站点为静态预览，默认不在浏览器实时遍历 JX3BOX 全量接口。
- `skipLoot`、`autoSell`、`protect` 是同一物品目录中的三个状态；`skipLoot` 独立，`autoSell` 与 `protect` 严格互斥。
- 21 个保护物品是首次启动的默认保护基线，而不是永久锁死列表；用户可以取消保护或给其他物品加保护。基线初始化后以用户状态为准。
- 自动出售默认配置中的 19 项不进入任何默认状态，也不得在导出时自动混入。
- 自定义物品不分类，永远不受任何分类、品质、装等、部位或副本批量规则影响；三个状态都必须手动指定。
- 支持导入已有 `.us.jx3dat`，但只解析受限目标表，不执行任意 Lua；默认采用合并，另提供替换，导入先预览后一次提交。
- 导出文件严格使用 `.us.jx3dat` 后缀，编码为 CP936/GBK、无 BOM、单行 Lua；空列表也必须按第 8 节的规则显式覆盖三个受管目标表。
- 指纹格式固定为：`『剑网3掉落工坊』 v0.2.0 by 凌千羽·龙争虎斗 <YYYYMMDD_HHmmss>`。版本紧跟项目名，同一批下载的两个文件共享 Asia/Shanghai 时间戳，指纹不区分模块；导入器继续兼容旧版 `JX3 Loot Forge` 标记。
- 本地状态无 TTL，刷新、重启和快照升级不能丢失；用户可以显式重置或备份/恢复工作区。

### 1.2 可后续调整但不阻塞开发的默认策略

- 导入同时出现同名出售和保护时，产品采用“保护优先”：预览明确显示冲突，确认前允许用户取消；提交后绝不产生 `autoSell=true && protect=true`。
- 离线包默认完全不联网；用户点击“检查/导入数据更新”时才处理外部数据包，在线版则按 manifest/hash 提示更新。
- 导入的 `replace` 只清理导入文件实际声明的目标表；未声明的表不被猜测清空。若文件包含多个目标表，则对这些表整体替换。
- 自定义库中的名称若与官方目录同名，规范化为同一物品并保留来源标记，但仍以 `customOverride=true/excludeFromBulk=true` 排除批量规则；用户显式移出自定义覆盖后，才可恢复官方批量管理。

## 2. 参考数据与生产数据原则

`data/raw` 中现有的四个 `.us.jx3dat` 文件只用于人工理解字段结构、核对导入/导出预期和设计测试断言。它们不是产品数据源，不是默认配置的运行时输入，也不能被复制进发布包作为“现成数据”。

生产数据必须由程序生成：

1. 默认保护 21 项使用源码中的类型化常量生成。
2. 副本、Boss、掉落和分类目录由数据管道从 JX3BOX API 采集、规范化和去重。
3. 快照、manifest、离线内嵌目录、测试夹具和导出配置都由生成器/测试构建产生；构建、运行、测试不能读取或复制 `data/raw`。
4. 测试需要的极小 Lua 样本应写成独立的受控 fixture，并注明它不是生产数据。

## 3. 数据采集、快照与更新

### 3.1 采集范围

维护者脚本/CI 必须遍历所有历史版本、所有副本、所有难度 MapID、所有 Boss 及其掉落，首期使用 `client=std`。不能只采集范阳夜变或示例中的 5 个 Boss。

数据源包括：

- 副本/难度/MapID 总目录：`https://node.jx3box.com/fb/info?client=std`
- Boss 校验接口：`/fb/boss?MapID={MapID}&client=std`
- 每个 MapID 的完整掉落：`/fb/drop/v2/{MapID}?client=std`（响应中的 `BossName` 建立 Boss 关联；无需按 Boss 重复请求）
- 物品元数据：`/item_merged/id/{ids}?client=std&per=50`（以返回 `meta.id` 对应掉落复合键，不能误用内部数字 `idKey`）

旧的 `/fb_map.json` 当前虽返回 HTTP 200，但业务响应是 `Not Found`，不得再作为地图索引。v0.1.0 于 2026-08-23 的完整快照审计结果为 254 个 MapID、981 个 Boss、43,033 条掉落记录和 16,571 个精确去重名称；发布新数据包时以当次抓取报告为准，而不是把这些数字硬编码成永久断言。

每条掉落保留物品名称、规范化名称、类别/子类（能从上游确定时）、品质、装等、部位以及版本/副本/难度/Boss 来源关系。无法可靠分类的项目进入“未分类”，不因此丢弃。

### 3.2 为什么是构建时采集

Boss/drop 子 API 的 CORS 只允许 JX3BOX 页面来源，且没有可依赖的统一 `ETag` 或 `Last-Modified`。因此不能把全量爬取放在任意用户浏览器，也不能承诺通过上游时间戳精确判断每个掉落接口是否更新。浏览器只读取随站点发布的静态快照。

爬虫需具备有限并发、重试、超时、失败清单和源数据摘要；任何部分失败都不能悄悄生成“看似完整”的快照。维护者在版本更新时运行全量采集并审核差异；浏览器只缓存已经通过完整性与 SHA-256 校验的发布快照。

### 3.3 快照与 manifest

建议生成以下字段：

```text
snapshot.schemaVersion
snapshot.client = "std"
snapshot.catalogVersion
snapshot.generatedAt（ISO 8601 抓取时间）
snapshot.contentHash（排除 generatedAt/catalogVersion 后稳定序列化的 SHA-256）
snapshot.sourceUrls / sourceSummary
snapshot.maps[] -> dungeons[] -> difficulties[] -> bosses[] -> drops[]
```

`manifest.json` 至少包含快照 URL、schema 版本、内容 hash、生成时间、条目统计、源摘要和校验信息。在线前端只比较 manifest/hash，hash 未变就继续使用本地缓存；变更时提示用户导入/更新。离线包将经过校验的快照内嵌到单文件。

新快照中新增的物品默认三状态全为 `false`，不得自动继承“自动出售装备”等危险的动态规则。快照中消失的历史选中名称保留在本地状态中，以“历史/自定义”方式可见，避免数据更新导致静默失去配置。

## 4. 领域模型与状态不变量

### 4.1 统一物品模型

目录的最小规范模型如下（字段名可在实现时用 TypeScript 类型表达）：

```ts
type ItemState = {
  skipLoot: boolean;
  autoSell: boolean;
  protect: boolean;
};

type Item = {
  id: string;                 // 规范化名称的稳定 ID
  displayName: string;        // 导出使用的精确名称
  state: ItemState;
  metadata?: ItemMetadata;    // 官方目录的类别、品质、装等、部位
  sources: SourceRef[];       // 可来自多个副本/Boss
  isCustom: boolean;
  customOverride: boolean;    // 与 excludeFromBulk 等价的明确标记
  systemSeed?: 'defaultProtection'; // 无 API 来源的 21 项默认保护基线
};
```

规范化只用于去重、匹配和状态键，不得在导出时改写用户/上游的显示名称或其有意义的空格。名称级游戏配置意味着同名物品跨副本全局生效：目录可以保留多来源，但状态只维护一份。

### 4.2 真值表

`skipLoot` 可以和另外一种出售策略同时为真；`autoSell` 和 `protect` 只能二选一：

| skipLoot | autoSell | protect | 含义 | 是否有效 |
|---:|---:|---:|---|---|
| 0 | 0 | 0 | 不跳过、不出售、不保护 | 有效 |
| 1 | 0 | 0 | 跳过拾取 | 有效 |
| 0 | 1 | 0 | 自动出售 | 有效 |
| 1 | 1 | 0 | 跳过拾取并自动出售 | 有效 |
| 0 | 0 | 1 | 保护不出售 | 有效 |
| 1 | 0 | 1 | 跳过拾取且保护不出售 | 有效 |
| 0/1 | 1 | 1 | 同时自动出售和保护 | **无效，必须拒绝/修复** |

交互上开启自动出售必须原子关闭保护，开启保护必须原子关闭自动出售，并显示文字提示、图标或状态标签，不能只靠颜色区分。领域命令、导入迁移、批量应用、持久化读回、导出前都执行同一不变量校验；任何非法输入都不直接写入当前状态。

### 4.3 首次启动默认值

对全部 `std` 官方目录物品初始化：`skipLoot=false`、`autoSell=false`、`protect=false`；自定义库为空。随后把以下 21 个精确名称设置为 `protect=true`。首启时如名称存在于官方目录，则合并为同一规范物品并保留官方来源；如名称不在副本掉落目录，也必须创建一个独立规范物品，标记 `systemSeed='defaultProtection'`（或等价的 `defaultProtection` 来源），并明确保持 `isCustom=false`、`customOverride=false`，不能把它错误标为用户自定义。

```text
炎枪重黎
腾空
圆月双角
五项斩
麒王逐魂
金红狩命
秋声烛影
旧禅镇
相映红
石剑·溟灵
秋露白
曳影残剑
赐清平
卦预乾坤
朝露昙华
夜话白鹭·鸿
金红狩命·鸿
秋声烛影·鸿
钧天·鸿
水长生 ·雪银莲
溯·鸿
```

`水长生 ·雪银莲` 中“生”和“·”之间的 ASCII 空格必须保留。保护基线只在该工作区第一次初始化时应用；之后以用户明确修改过的状态为准，数据更新不得把取消的保护强行恢复。自动出售默认配置中的 19 项永不作为默认状态或隐式规则导入。

没有官方元数据或副本来源的系统基线项仍可逐项取消/调整，状态必须持久化并能导出；它们不进入基于副本、分类、品质、装等或部位的批量作用域。若未来快照出现同名官方条目，按规范化名称合并来源和元数据，但用户已经保存的状态优先，不能因合并再次覆盖用户选择。

## 5. 自定义物品

自定义物品支持单条和多行输入，按规范化名称去重，允许未知名称。自定义模型不提供“装备/材料/秘籍”等分类，也不参与任何副本、类别、品质、装等、部位批量规则；`skipLoot`、`autoSell`、`protect` 必须逐项手动设置，仍遵守 `autoSell`/`protect` 互斥。

输入校验包括：长度和行数上限、控制字符拒绝、GBK 可编码性检查、空白/重复提示、Lua 字符串安全转义。与官方同名时合并来源和元数据，但只要仍在自定义覆盖库就保留 `customOverride=true`，批量规则跳过它。未知名称在导入文件时自动进入自定义库并设置该标记。

## 6. 多副本批量配置交互

### 6.1 选择范围

左侧使用版本/副本/难度/Boss 树：支持父级三态、搜索、全选当前结果、反选当前结果和收藏的副本组合。选择范围变更后，主区展示掉落记录数、规范化后唯一名称数、跨范围重复名称数及受自定义覆盖排除的数量。提供品质、装等、部位过滤和“只看未配置/有冲突/已保护”等状态过滤。

同名物品按规范化名称去重，但保留所有来源路径；对一个名称的变更要在应用前提示“该状态会作用于所有关联副本/Boss”。

### 6.2 规则矩阵

矩阵行至少包括：装备、材料、秘籍、消耗品、货币/兑换、其他、未分类；装备下可展开武器、防具、饰品等子类。列为：跳过拾取、自动出售、保护不出售。每个单元格不是普通复选框，而是三态操作：

```text
保持不变 | 开启 | 关闭
```

应用规则只针对当前官方范围内且未被 `customOverride/excludeFromBulk` 排除的物品，并把结果一次性物化为物品级状态；不保存会在未来数据上自动套用的危险动态规则。用户可以先设置“装备自动出售、材料和秘籍不变”“材料跳过拾取”等组合，再独立下载两个模块。

### 6.3 预览与提交

点击应用前生成精确 diff：新增/取消的每个状态、自动出售与保护的互斥修复、跨副本影响、自定义排除数和受保护冲突。确认后原子提交并立即持久化，提供一步撤销；失败不得写入半套结果。单项编辑也走相同领域命令，确保 UI 和批量操作一致。

## 7. 已有 `.us.jx3dat` 导入

导入器只识别以下三个受管目标表（分布在两类配置文件中）：

- 跳过拾取：`MY_GKPLoot.tAutoPickupFilters`
- 自动出售：`MY_AutoSell.tSellItem`
- 保护不出售：`MY_AutoSell.tProtectItem`

不执行任意 Lua，不调用 `eval`/`Function`，不解析表达式、函数、循环或外部调用。实现受限语法解析器，只接受目标表、字符串键/值和必要的表结构；未知表和其他语句忽略并报告。合成指纹只在建状态和生成 diff 之前忽略：它不是物品、不是 `ItemState`，不参与 `autoSell`/`protect` 互斥判断，也不能进入自定义库。语法异常、控制字符、超长输入或 GBK 解码问题使本次导入失败且不污染当前状态。

支持两种模式：

- **合并（默认）**：文件中出现的名称设置相应状态，当前未出现的状态保持不变。
- **替换**：清空文件实际声明的目标表对应状态，再应用文件内容；若文件声明多个目标表，则只替换这些表，未声明的目标表保持不变。

导入未知名称时进入自定义库并标记 `customOverride=true`。若输入同时把同一名称放入出售表和保护表，预览显示冲突并采用保护优先；用户确认后才提交，绝不静默留下两个为真的非法状态。导入过程为“读取—校验—生成 diff—确认—一次提交”，任一步失败都回滚。

## 8. 导出与文件格式

### 8.1 两份文件、三个受管目标表

两个下载文件分别承载一个或两个受管目标表：

- 跳过拾取文件：`MY_GKPLoot.tAutoPickupFilters` 的第一项是合成指纹，之后才是 `skipLoot=true` 的名称。
- 自动出售文件：`MY_AutoSell.tSellItem` 的第一项是同一合成指纹，之后才是 `autoSell=true` 的名称；`MY_AutoSell.tProtectItem` 不放指纹，只输出 `protect=true` 的名称。

合成指纹不属于任何 `ItemState`，不参与 `autoSell`/`protect` 互斥判断，也不能被计入物品数量、导入状态或批量规则。它只允许出现在上述两个主表的第一项，不能出现在保护表。

两个文件可以独立下载，也可以同一批同时下载。保护表必须始终显式输出，即使没有任何受保护物品也输出空表，以覆盖旧配置。因而全空时的精确结果是：跳过拾取主表仅含指纹，自动出售主表仅含指纹，保护表为显式空表。保护物品不进入出售表；默认 19 项不自动添加。指纹使用类型化导出常量生成，不能从 `data/raw` 复制。

### 8.2 编码、排序和指纹

导出器先生成规范配置对象，再以确定性顺序（规范化名称排序，或明确稳定的用户可复现排序）序列化为单行 Lua，使用 CP936/GBK 编码、无 BOM。字符串必须进行 Lua 安全转义；无法编码的名称在导出前报错并阻止下载。扩展名必须严格为 `.us.jx3dat`，文件名包含模块和批次时间戳但不改变内容指纹。

指纹精确格式如下：

```text
『剑网3掉落工坊』 v0.2.0 by 凌千羽·龙争虎斗 <YYYYMMDD_HHmmss>
```

时间按 Asia/Shanghai 生成，单批下载的两个文件使用同一个时间值；升级项目版本只改版本常量和构建产物，不让用户手填。指纹不区分“自动出售/跳过拾取”。

## 9. 本地持久化与备份

使用带 schema 版本的 storage adapter，将用户状态与生成的目录分离。至少持久化：

- 每个规范化物品的三个状态；
- 自定义名称、`customOverride` 和来源标记；
- 当前筛选、最后浏览位置、收藏副本组合和 UI 偏好；
- 数据快照版本、迁移版本和工作区元信息。

刷新、浏览器重启和目录升级不丢数据，无 TTL。升级时按规范化名称映射；快照消失的已选名称保留为历史/自定义可见。提供显式“重置工作区”，并在 UI 中说明清除 HTTP 缓存不等于清除 Local Storage/IndexedDB 的站点数据。

`file://` 移动或重命名后可能被浏览器视为新的源，不能依赖浏览器存储作为唯一备份；必须提供工作区 JSON 导出/导入，导入同样做 schema、长度和互斥校验。GitHub Pages 与 Cloudflare Pages 是不同源，状态不自动共享。

## 10. 技术架构与目录边界

采用纯静态前端。正式离线构建将 CSS、JavaScript、字体/图标所需资源和经过校验的目录数据内联到单个 `index.html`，避免 `file://` 下 ESM 动态加载、`fetch` 本地文件和 Service Worker 依赖。开发版可拆分模块，但构建必须产生可双击的单文件。

建议目录边界如下：

```text
src/
  catalog/          # 快照 schema、规范化、来源关系、分类视图
  domain/           # ItemState、命令、不变量、初始化和迁移
  bulk-rules/       # 范围解析、分类矩阵、diff、撤销
  importer/         # 受限 .us.jx3dat lexer/parser/校验/预览
  exporter/         # 两份文件、三个目标表、指纹、确定性 Lua 序列化
  encoding/         # GBK/CP936 编码检测与转换
  storage/          # 版本化 Local Storage/IndexedDB、备份恢复
  ui/               # 树选择、矩阵、物品表、导入导出和无障碍
tools/
  crawler/          # 全量 API 采集、限速、重试、失败报告
  snapshot/         # 规范化、去重、hash、manifest 和内嵌数据生成
tests/
  unit/ integration/ fixtures/
docs/
  DEVELOPMENT_PLAN.md
dist/               # 构建输出；可生成 offline/index.html
```

模块之间只通过类型化 DTO/领域命令交互。`data/raw` 不得出现在构建依赖图、运行时依赖图或测试脚本输入中。

### 10.1 安全与健壮性

- 对上传文件大小、文本长度、行数、名称数量、单批操作数量设置上限，避免内存和 UI 阻塞。
- UI 使用文本节点/框架转义，名称不得当作 HTML；导入内容、指纹和来源均防 XSS。
- 规范化键使用安全 Map/`Object.create(null)`，拒绝原型污染字段。
- 受限 Lua parser 不执行代码；字符串转义覆盖反斜杠、引号、换行和控制字符。
- 文件名只由受控版本、模块和时间戳组成；校验 `.us.jx3dat`，不使用用户输入构造路径。
- GBK 转换失败、非法 Unicode、非法互斥状态在边界拦截；导出前再次校验。
- 爬虫限制速率、重试次数和并发，保存失败清单；快照 hash 和 schema 校验防止部分数据发布。

## 11. UI 视觉与信息架构

参考 `jx3mwtime`：近黑背景、暗色玻璃拟态面板、金色强调色、约 1400px 最大宽度、约 300px sticky 侧栏、12px 圆角。中文文案优先，状态标签要同时包含文字、图标/边框或 aria 属性；三态、互斥、冲突不能只靠颜色表达。

主要区域：

1. 顶栏：项目名、版本、数据版本/hash、离线/在线状态、备份/重置入口。
2. 左栏：版本—副本—难度—Boss 树、搜索、当前结果全选、收藏组合、品质/装等/部位/状态过滤。
3. 主区：范围统计、去重后的物品表、来源展开、三状态逐项控制和自定义标记。
4. 批量面板：分类规则矩阵、当前作用范围、排除自定义项数量和危险操作提示。
5. 底部/抽屉：精确 diff、冲突预览、撤销、导入合并/替换、跳过拾取/自动出售单独下载及双文件下载。

键盘可以完成树导航、搜索、表格状态切换、矩阵操作和确认/取消；表头、按钮、三态控件和错误信息提供可读的 `aria-label`/`aria-live`。小屏幕使用折叠面板，但不隐藏危险状态说明。

## 12. 托管、发布与许可证

- JX3BOX 帖子附件：正式离线发行渠道，附件中包含可双击的 `index.html`、源码压缩包、数据包/版本说明和使用说明。
- GitHub：源码、AGPL-3.0 `LICENSE`、构建脚本和 CI；GitHub Pages 作为主预览站。
- Cloudflare Pages：静态镜像预览。DNS 仍由 DNSPod 管理，可用不同子域分别 CNAME 到两者；不同源不共享浏览器状态。
- 不建议用家宽公网 IP 作为正式站点；未备案时境外静态预览的大陆可达性不保证。Cloudflare Pages/Workers 也不能替代备案要求。
- Cloudflare Workers 不承担全量实时爬取；若使用，只做轻量 manifest/代理，并遵守单次请求的子请求限制。全量采集在维护者脚本或 CI 完成。
- AGPL-3.0 交付要求包含许可证正文、源代码获取说明和修改/网络提供版本的相应源码告知义务。

## 14. 风险与非目标

主要风险是上游字段变化、CORS/限流、掉落分类不完整、同名物品的全局影响、GBK 编码损失、用户误把物品设为自动出售，以及 `file://` 不同路径造成存储源变化。对应措施是 schema/hash 校验、构建时采集、来源保留、预览/撤销、互斥不变量、GBK 预检、备份恢复和离线单文件验收。

第一版非目标：怀旧端数据；浏览器端实时全量爬虫；依赖服务器的账号/云同步；IE 兼容；家宽公网正式部署；自动推断用户意图并给新物品套用出售规则；把 `data/raw` 当作运行时数据；承诺不存在的上游更新时间戳；替用户决定哪些物品一定可以出售。
