# 第一版反馈记录与第二版完善方案

> 记录日期：2026-08-24  
> 当前产品版本：v0.1.0  
> 文档状态：第一版反馈已落盘，第二版方案待确认和分阶段实施

## 1. 本次落盘的边界

本文件把第一版使用反馈、已确认的产品方向和第二版的设计约束保存到项目中。本轮不直接修改页面、领域状态模型或数据快照，避免在迁移规则尚未确认前破坏已有工作区和导出兼容性。

第一版仍作为可回退基线保留。第二版实施前，必须先补充迁移测试、导出回归和离线包回归；任何新交互都要能从预览中看清将要改变的物品数量和状态。

## 2. 第一版反馈记录

| 编号 | 反馈 | 当前观察 | 第二版方向 |
| --- | --- | --- | --- |
| 1 | 各模块大小应随窗口缩放；当前字太小 | 当前主容器使用约 1400px 最大宽度，界面中大量字号为 8–13px。宽屏下内容集中在中间，文字密度高 | 使用响应式容器、CSS 变量和 `clamp()` 调整字号与间距；保留用户可选的舒适/紧凑密度，不用整体 `transform: scale()` 掩盖布局问题 |
| 2 | 自动出售与保护不出售互斥；两个模块可以合并 | 当前领域层已有互斥校验，但 UI 仍以两个独立列展示，用户容易把它们理解成可同时开启 | 把二者合成一个“处理方式”单选组：自动出售、保护不出售、不做特殊处理；“跳过拾取”继续作为独立开关 |
| 3 | 界面臃肿，希望优先快速生成配置 | 当前页面把范围树、筛选器、规则矩阵和逐项表格同时展开，灵活但首次使用的决策路径较长 | 把“快速生成”作为主流程；精细筛选和逐项编辑收进高级入口。所有批量动作先生成 diff，确认后一次提交并可撤销 |
| 4 | 版本应按等级归并，而不是展示很多同等级版本 | 当前 `CatalogMap` 只有 `expansion`、副本、难度等字段，没有可直接使用的等级字段；因此不能在 UI 中安全地假装已经完成等级归并 | 数据层增加等级/等级组和标准名称。每个等级的第一个版本作为等级名，例如用户给出的规则是“130 级第一个版本叫丝路风雨，则显示丝路风雨等级”；同等级的其他版本仍保留为来源详情 |
| 5 | 启动速度慢，需要找原因 | 首屏同步导入完整目录，并在首轮渲染构建物品、版本树、可用部位和筛选结果 | 先拆分运行时数据和索引，再做懒加载、缓存和 Worker/空闲时 hydration；开发服务器和正式离线包分别优化 |

截图中还可以看到一个直接的可用性问题：在较宽窗口下，页面外围留白较大，而表格内文字和控件仍然很小。第二版应优先提高信息的可读性和操作层级，而不是继续增加面板数量。

## 3. 第二版产品目标

第二版的主目标是“先快速得到一份可用配置，再允许用户深入调整”。建议把首页主路径压缩为：

1. 选择作用范围：全部副本、某个等级，或当前勾选的副本。
2. 选择一个快速规则：例如“当前最高等级装备保留，其余装备自动出售”。
3. 查看影响数量和状态 diff。
4. 确认、保存并导出；需要细节时再进入精细配置。

顶部主按钮建议改为“快速生成”，旁边保留“精细配置”“导入配置”“工作区”作为次级入口。快速生成面板只呈现当前步骤需要的选项，避免把所有筛选器同时放在首屏。

### 3.1 统一处理方式

第二版领域模型建议将两个互斥布尔值收敛为一个枚举，同时保留跳过拾取的独立状态：

```ts
type SellPolicy = 'neutral' | 'sell' | 'protect';

type ItemStateV2 = {
  skipLoot: boolean;
  sellPolicy: SellPolicy;
};
```

含义如下：

| 跳过拾取 | 处理方式 | 含义 |
| --- | --- | --- |
| 关闭/开启 | 不做特殊处理 | 不加入出售或保护表；跳过拾取仍可独立开启 |
| 关闭/开启 | 自动出售 | 进入出售表 |
| 关闭/开启 | 保护不出售 | 进入保护表 |

与现有工作区迁移时：

- `autoSell=true, protect=false` 映射为 `sell`；
- `autoSell=false, protect=true` 映射为 `protect`；
- 两者都为 `false` 映射为 `neutral`；
- 两者同时为 `true` 时不能静默丢失信息，迁移预览应显示冲突并采用“保护优先”，等待用户确认。

导出格式可以继续兼容现有游戏文件：`sell` 写入出售表，`protect` 写入保护表，`neutral` 不写入任何一张表。这样 UI 和领域模型变简单，外部文件格式不必在第二版同时变化。

### 3.2 快速规则预设

建议首批只放 4 个高频预设，避免再次做成规则矩阵：

1. **当前最高等级保留，其余装备自动出售**：以当前作用范围内装备的最高可比较等级为基准，低于最高等级的装备设为 `sell`；最高等级装备保持 `neutral`，无装等的物品不被误伤。
2. **只保留当前最高等级装备**：低于最高等级的装备设为 `sell`，最高等级装备设为 `protect`，适合需要明确防止误卖的场景。
3. **只处理装备，其他类别不变**：装备按用户选定的出售/保护方式处理，材料、秘籍、消耗品、货币和其他类别保持当前状态。
4. **恢复不做特殊处理**：清除当前范围内的出售和保护状态，跳过拾取状态保持不变；用于快速撤销危险规则。

“当前最高等级”必须明确作用范围：默认是用户当前选择的等级/副本范围，而不是偷偷使用全目录最高值。若范围内有多个装等区间，使用 `itemLevelMax` 参与比较，并在预览中列出“无法比较而被排除”的数量。

快速规则不保存成未来自动套用的动态规则，而是在确认时物化为物品级状态。这样数据更新不会把危险的出售策略悄悄套到新物品上。

### 3.3 预览和撤销

任何快速规则都必须先显示：

- 将改变的物品数，以及出售/保护/恢复各自的数量；
- 最高等级的判定值和作用范围；
- 无装等、系统基线、自定义覆盖和历史状态的排除数；
- 同名物品跨副本生效的来源数量；
- 是否存在旧版 `autoSell`/`protect` 冲突。

确认后原子写入工作区，保留一步撤销。下载按钮只在状态提交成功后启用，避免出现“页面显示已应用但导出仍是旧状态”的中间态。

## 4. 响应式界面方案

### 4.1 尺寸策略

不要对整个页面使用 `transform` 或 CSS `zoom`。建议建立一组可调 CSS 变量，并在宽度和用户密度偏好之间做有限范围缩放：

```css
:root {
  --ui-body-size: clamp(14px, 0.25vw + 13px, 16px);
  --ui-label-size: clamp(12px, 0.2vw + 11px, 14px);
  --ui-gap: clamp(10px, 0.8vw, 20px);
}
```

正文和主要操作文字设置可读下限，辅助说明可以更小但不再普遍使用 8–9px。用户偏好只切换“舒适/紧凑”两档，修改变量而不是改变元素坐标。

### 4.2 布局行为

- 容器使用 `width: min(100% - 32px, 1680px)`，让宽屏能利用空间，避免 1400px 内容被缩在中间。
- 宽屏显示侧栏和主区；中等宽度把侧栏变成可展开抽屉，快速生成摘要保持在顶部。
- 规则卡片使用 CSS Grid/Container Query；窄屏将三列处理方式堆叠成卡片，不强迫用户横向滚动整张宽表。
- 物品列表在窄屏显示“名称 + 当前处理方式”为主信息，来源和细节折叠到行内展开区。
- 表格、按钮和输入框保留可点击的最小尺寸；不通过缩小字体来解决空间不足。
- 首次打开按舒适密度渲染，并把用户选择记录到工作区的 UI 偏好中。

## 5. 按等级归并版本

### 5.1 当前限制

当前 `CatalogMap` 类型只有 `mapId`、`name`、`expansion`、`difficulty`、Boss 和物品 ID，没有等级字段。物品有装等，但不能仅凭页面当前聚合结果可靠地断言一个副本所属等级。因此第二版必须先改数据快照和爬虫产物，再改 UI 分组。

### 5.2 数据模型建议

在快照中增加可审计的字段，示意如下：

```ts
type CatalogMap = {
  // 现有字段...
  level?: number;
  levelGroupId?: string;
  levelName?: string;
  sourceVersion?: string;
  versionRank?: number;
};
```

生成规则建议按以下优先级执行：

1. 优先使用上游明确的等级/版本顺序字段；
2. 没有明确字段时，结合该副本装备装等区间和维护者映射表推导候选等级；
3. 每个等级按时间/版本顺序取第一个版本名作为 `levelName`，形成“丝路风雨等级（130级）”这类展示名；
4. 同等级其他版本合并到同一组，但原始 `expansion`、副本、难度和 Boss 来源必须保留，可在组内展开查看；
5. 无法判定或存在冲突时进入“待校正版本”，原始版本名继续显示，不能强行归入错误等级。

用户给出的“130级第一个版本叫丝路风雨”作为产品规则样例，落地时仍需以本次快照的实际上游字段和维护者确认表为准，不能凭名称猜测。

建议把等级校正表作为版本化数据的一部分，发布新目录时输出“新增、合并、未判定、人工修正”的差异报告。工作区保存的是稳定的 `mapId` 和物品 ID，版本组名称变化不应清空用户状态。

### 5.3 UI 呈现

左侧树第一层显示“等级”，第二层显示该等级下的副本/难度；原始版本名在组标题或详情中作为来源标签显示。搜索同时匹配等级名、原始版本名、副本名和 Boss，避免归并后老用户找不到旧称。

## 6. 启动慢的原因与优化顺序

### 6.1 当前检查得到的证据

- `web/src/catalog/catalog.std.json` 约 8.8 MB；`web/public/data/catalog.std.json` 也约 8.8 MB。后者是发布/更新数据，前者被前端通过 `import rawSnapshot` 直接打进首屏模块。
- `buildCatalogItems()` 首次把整个快照的物品数组重新建立为 Map；`LootForgeApp` 随后构建 `activeCatalogItems`、`allItems`、版本树和可用部位。
- `filteredItems` 的筛选会逐项规范化名称，并在需要时遍历来源；状态或筛选变化时会再次走全量数组。
- `vinext`、RSC 和 Cloudflare Vite 插件会增加开发服务器初始化成本；这和浏览器首屏解析是两段不同的问题。
- 当前还没有稳定的生产环境基准，所以不能把一次开发服务器请求时间当作正式性能结论；第二版应先加入性能标记再比较。

### 6.2 按收益排序的优化

**P0：拆分运行时目录。** 构建时生成轻量的等级/副本/物品摘要索引，首屏只加载索引和当前范围需要的物品；来源详情和完整目录按需加载。发布更新仍可保留完整数据包，但不让 8.8 MB 原始 JSON 阻塞首屏。

**P0：预构建索引。** 在爬虫/构建阶段生成规范化名称、搜索文本、等级组、类别计数、可用部位和来源反向索引。运行时不要为每个物品重复执行 `normalize()`、`sources.some()` 和 Map 重建。

**P1：延后非关键工作。** 先渲染快速生成和摘要，工作区恢复、IndexedDB 目录校验、来源详情和历史状态在 `requestIdleCallback` 或分段任务中完成；大目录解析必要时放进 Web Worker。

**P1：减少 React 重算。** 将静态索引放到快照激活时一次构建并缓存，筛选结果按查询键缓存；状态变更只更新受影响的计数和可见行，不复制全量物品对象。

**P2：区分开发和发布链路。** 本地开发只加载必要的 Vite/vinext 插件；Cloudflare/托管配置在发布构建中启用。离线包继续生成单文件，但其内部使用预构建索引和分段初始化。

### 6.3 性能验收指标

第二版实施前先记录基线，随后至少满足：

- 开发服务器“可访问”时间和浏览器“首个可操作界面”时间分别统计，不混为一个数字；
- 首屏初始传输和解析不再直接承受完整 8.8 MB 目录，目标是把首屏目录载荷压到 1 MB 级别以内；
- 首屏不出现超过约 200ms 的连续主线程长任务；
- 快速生成按钮在常见范围内打开预览的响应保持在可感知但不阻塞的范围内，并在大范围操作时显示进度；
- 完整目录加载、离线双击、刷新恢复和导出仍通过回归测试。

上述是工程验收目标，不是当前已经达到的指标；实际数值以同一台参考机器和同一份快照的测量报告为准。

## 7. 分阶段实施顺序

1. **冻结第一版基线**：保存当前工作区/导出 fixture，补充性能标记和截图基线。
2. **先做领域迁移**：引入 `sellPolicy`，完成 v1 工作区到 v2 的迁移、冲突确认和旧格式导出回归。
3. **再做数据归并**：扩展快照和构建脚本，生成等级组、首个版本名、来源详情和未判定报告。
4. **上线快速生成**：先实现四个预设、作用范围、diff、确认和撤销，再把精细配置放入高级入口。
5. **调整响应式界面**：提高字号和点击区域，按宽度折叠侧栏、规则卡片和物品详情。
6. **优化首屏**：落地轻量索引、按需加载、缓存和 Worker/空闲 hydration，并分别测量开发和离线构建。
7. **完整验收**：多浏览器、窄屏、断网 `file://`、旧工作区迁移、导入冲突、导出文件和性能指标一起验收。

## 8. 需要在实施前确认的事项

- “当前最高等级”默认按用户当前选择的等级/副本范围计算，还是按整个目录计算；建议默认按当前范围。
- “最高等级装备保留”是保持不做特殊处理，还是自动设置为保护不出售；建议两个预设分别提供，避免隐含危险动作。
- 跳过拾取是否继续独立存在；本方案按用户反馈保留独立开关。
- 等级归并的权威来源和人工校正负责人；没有可靠来源时宁可显示“待校正”，不要猜测。

## 9. 第二版完成标准

- 自动出售、保护不出售、不做特殊处理在 UI、领域层、持久化和导出前校验中始终是单选；旧版冲突迁移可预览、可确认、可回退。
- 用户在不展开高级配置的情况下，可以在几步内生成“最高等级保留、其余装备出售”的配置，并看到精确影响数量、排除项和一步撤销。
- 宽屏、笔记本和窄屏下正文与主要控件可读、可点，字号不靠整体缩放解决；用户密度偏好可保存。
- 左侧第一层按等级归并，原始版本名和来源关系仍可查；无等级信息的项目明确进入回退组。
- 首屏不再同步解析完整目录；性能报告能区分服务器启动、首屏加载、目录解析和首次可操作时间。
- 旧版导出的 `.us.jx3dat` 仍可导入，离线单文件仍可编辑、刷新恢复和导出。

下一步建议先确认第 8 节的四个决策，再按第 7 节从领域迁移和数据归并开始。确认后再进入 UI 改造，避免先做视觉调整、随后因状态和等级模型变化而返工。
